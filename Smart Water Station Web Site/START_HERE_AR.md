# تشغيل الموقع والموديلات

هذه نسخة معدلة من Smart-Water-Station-Analytics. الموديلان الموجودان في backend/models هما نفس ملفات نتائج تدريبك المرفوعة، وليسا تدريبًا جديدًا. مخرجات الجودة والإنذار تجريبية على بيانات صناعية، وليست اعتمادًا لصلاحية مياه حقيقية للشرب.

## الملفات
- website: الموقع كاملاً (HTML وcss وjs وassets) في مجلد واحد بدون نسخ مكررة. افتح website/index.html. ارفع محتويات هذا المجلد فقط على الاستضافة، ولا ترفع backend أو training لاستضافة عامة.
- backend/service.py: برنامج تشغيل الموديلات، قراءة Firebase، ونشر نتائج جديدة كل دورة.
- backend/models: الموديلات المدربة الفعلية.
- backend/evaluation: نتائج تدريبك الأصلية وصور المقارنة والتقييم.
- training: كود التدريب والكولاب والداتا النظيفة، لإعادة التدريب عند الحاجة. لا يُعاد التدريب مع كل قراءة.
- backend/verification_results.json: نتيجة إعادة مطابقة قرارات الاختبار للموديلات.

## أول تشغيل على Windows
ثبّت Python 3.12، وافتح Terminal داخل backend، ثم نفّذ:

```powershell
py -3.12 -m venv .venv
.\.venv\Scripts\python -m pip install -r requirements.txt
```

من Firebase Console لنفس المشروع، افتح إعدادات المشروع ثم Service accounts، وأنشئ مفتاحًا لحساب الخدمة على جهازك إذا لم يكن لديك مفتاح تشغيل موجود. هذا الملف خاص: لا ترفعه للويب ولا ترسله في المحادثة.
ضع ملف الاعتماد في مكان خاص على جهازك، ثم عرّف مساره في نفس نافذة Terminal وشغّل البرنامج:

```powershell
$env:GOOGLE_APPLICATION_CREDENTIALS="C:\private\firebase-service-account.json"
.\.venv\Scripts\python service.py
```

البرنامج يستخدم Firebase Admin بصلاحيات حساب الخدمة؛ لا يحتاج فتح قواعد Firebase للعامة. صلاحيات إدارة الجدول على الواجهة تتبع قواعد قاعدة البيانات الحالية؛ لم نغيّر القواعد أو نضف نظام أدوار جديدًا.

افتح مجلد website باستخدام Live Server أو استضافتك المعتادة. في صفحة التحليلات:
1. تحقق من سعة الخزان ونسبة الاحتياطي واحفظ الإعدادات. القيم المعروضة أوليًا من إعدادات الموقع: قطر 6 م وارتفاع 5 م، حوالي 141.372 م³، واحتياطي 10%. الحساب الخطي يتطلب خزانًا رأسيًا ثابت المقطع.
2. أدخل تاريخ وكمية كل موعد تعبئة، واختر العقد المدفوع المقابل. العقود القديمة لا تحتوي تاريخ تعبئة صريحًا؛ لن نحوله إلى موعد افتراضي.
3. بعد مراجعة جميع المواعيد، اضغط تأكيد مراجعة الجدول؛ يمكن تأكيد جدول بلا حجوزات إذا كان ذلك صحيحًا.
4. شغّل المحاكي وتأكد أن live_telemetry تحتوي قراءات وtimestamp Unix بالملّي ثانية حديثًا.
5. مع تشغيل service.py، تظهر النتائج في ai_results ويعرضها الموقع تلقائيًا.

عدد الأفراد ثابت 5 يوميًا. متوسط كمية الفرد يأتي من العمليات المكتملة الفعلية الموسومة فردي، غير المرتبطة بعقد، وغير التقديرية. السجل المتاح محدود، لذلك خطة الغد حساب أولي وليست مودل طلب مدربًا. إذا لم يتوفر completed_at، تستخدم created_at للتاريخ، وهو قيد للسجلات القديمة.

المخزون يُحسب مرة واحدة من المنسوب وسعة الخزان، ويُعتبر متاحًا فقط عند قبول الجودة في الجهاز والمودل معًا. المطلوب = max(0، الحجوزات + كمية الأفراد + الاحتياطي - المخزون المتاح). حالة جودة غير مقبولة تُظهر quality_blocked: الكمية المعروضة للتخطيط فقط وليست إذن تشغيل. برنامج التحليل لا يرسل أوامر مضخات.

إدخال المنفذ الفعلي لموعد التعبئة يتم من زر تحديث المنفذ في الجدول بعد مراجعة سجل التسليم. لا يُرحّل الحجز تلقائيًا. المياه المتبقية فعليًا تدخل في منسوب الخزان فقط.

## شرط مهم للإنذار المبكر
المودل المدرب يحتاج 12 قراءة حقيقية متتالية بفاصل 5000 ملّي ثانية، ويستخدم آخر 55 ثانية لتوقع تجاوز خلال 60 ثانية قادمة، عندما تكون القراءة الحالية ضمن الحدود.

timestamp في كود المحاكي السابق كان وقت استلام Firebase، وإرسال HTTP قد يتأخر؛ لذلك قد تعمل الجودة الحالية بينما يبقى الإنذار في حالة التجميع. هذه ليست نتيجة تدريب فاشلة. لا نعوّض الفجوات أو نقرّب التوقيت سراً. لتشغيل الإنذار على المحاكي يلزم تعديل تسجيل الوقت ليكون وقت أخذ العينة الحقيقي على جدول 5 ثوانٍ، وفصل أخذ العينات عن رفعها؛ أو إعادة التدريب والتحقق على فواصل القياس الفعلية المتفاوتة. لم نعدّل كود ESP32 في هذه الحزمة.

## ما تم التحقق منه
- تشغيل ملفي joblib بإصدار scikit-learn 1.6.1 المطابق لتدريبك.
- إعادة حساب مدخلات كل سجلات اختبارك: 2917 للجودة و789 للإنذار. جميع قرارات التصنيف طابقت CSV النتائج المرفوع. الفرق العددي الأقصى في الدرجة حوالي 1.1e-16.
- اختبار تشغيل المودلين على نافذة صحيحة، الحساب التخطيطي، رفض قراءة قديمة أو خارج المدى، نافذة بفجوة، جدول مفقود، وحظر الجودة.
- فحص جميع ملفات JavaScript نحويًا، واختبار قبول الواجهة لصيغة نتيجة المودل وإخفائها بعد انتهاء الصلاحية.
- معاينة صفحة التحليلات مع القراءة من Firebase. القراءات الحالية وقت المعاينة قديمة، ولم توجد نتائج حديثة لبرنامج التحليل.
- لم يتم تشغيل خدمة دائمة على حسابك أو نشر نتائج اختبار مصطنعة في Firebase. يحتاج التشغيل الحي ملف الاعتماد وتشغيل المحاكي والخدمة؛ لا يكفي رفع HTML.

لإعادة اختبارات Python من backend:

```powershell
.\.venv\Scripts\python verify.py
.\.venv\Scripts\python reproduce_predictions.py
```

ملف offline_example_results.json مثال اختبار اصطناعي فقط، ولا يقرأه الموقع ولا يرفعه البرنامج تلقائيًا.

## Render
ارفع محتويات backend كمشروع Python Worker، مع مجلد models. ملف render.yaml قالب إعداد للخدمة وليس إثبات نشر. أضف ملف اعتماد Firebase كـ Secret File باسم firebase-service-account.json، ويشير GOOGLE_APPLICATION_CREDENTIALS إلى /etc/secrets/firebase-service-account.json. لا تحفظ المفتاح في Git. يلزم اختيار خطة خدمة مناسبة من حسابك؛ لم ننشئ اشتراكًا أو ننشر خدمة.

## حدود النتائج
الجودة الحالية تطابق حدود المشروع: TDS ≤300، pH من 6.5 إلى8.5، عكارة ≤1.5، أكسجين ≥5. نسبة واجهة القواعد هي نسبة الحساسات المطابقة، وليست احتمال صلاحية للشرب.

الإنذار اختُبر على البيانات الصناعية: استدعاء نحو90.55% ودقة إيجابية نحو57.21%؛ قد ينتج إنذارات كاذبة. درجة predict_proba غير معايرة. لا يوجد مودل مدرب لتشخيص الفلتر أو أعطال المضخات، وتظهر هذه الوظيفة غير متاحة. مخطط توقع الطلب مقابل الفعلي لا يختلق سجلات مقارنة؛ يحتاج بيانات مؤرخة موثقة لاحقًا.
